# Issue 56: GitHub merge queue and final-candidate binding

Research date: 2026-10-28 UTC. Scope: GitHub primary documentation and read-only API observations; no queue was exercised. This supplements `git show 0dcb138:docs/research/issue-56-final-integration-evidence.md` and does not establish a working final gate.

## Conclusion

GitHub documents queue checks on an integrated merge-group SHA, including the latest base and earlier queued changes. It does **not**, in the cited material, specify a general atomic guarantee that a separately reviewed and black-box-tested tree is exactly the tree ultimately landed under every merge method and batching configuration. Queue use alone also does not establish independent review or trustworthy runtime provenance. The repository's effective rules and queue settings could not be inspected through the relevant endpoints; do not assume a queue is enforced.

## Documented behavior

- When a PR enters the queue, GitHub builds a temporary merge group containing the latest target branch and changes from PRs ahead of it. The queue checks required status checks against that integrated group. Actions uses the separate `merge_group` event: `GITHUB_SHA` is the merge-group SHA and `GITHUB_REF` its ref. Workflows providing required checks must subscribe to `merge_group`; otherwise those checks are not reported and the merge fails. Third-party CI can build the temporary `gh-readonly-queue/{base_branch}` branch, whose SHA differs from the PR's. Sources: [queue documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue#how-merge-queues-work), [Actions event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group).
- The `checks_requested` webhook directs the recipient to check the **head SHA** and report a check run or commit status. GitHub's published schema defines `merge_group.head_sha` as the group SHA, `head_ref` as its full ref, `base_sha` as the SHA of the merge group's **parent commit**, and `base_ref` as the full target-branch ref. Do not equate `base_sha` without further proof to a separately sampled current branch tip or assume a particular parent topology. Sources: [webhook event](https://docs.github.com/en/webhooks/webhook-events-and-payloads#merge_group), [GitHub's OpenAPI schema](https://github.com/github/rest-api-description/blob/main/descriptions/api.github.com/api.github.com.json) (`merge-group`, `webhook-merge-group-checks-requested`).
- GitHub says the queue proceeds when required checks pass; queue and PR checks are coupled in branch protection/rulesets. Required checks and their actual implementations are configuration-dependent. A configured timeout can cause removal, and failures, conflicts, user removal, or unresolvable protection failures can remove an entry. In GitHub's example, failure of PR 1 removes it and recreates PR 2's temporary group without PR 1; the new group is checked. Queue jumps rebuild in-progress groups. Source: [managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue#how-merge-queues-work).
- Queue settings select merge, squash or rebase; build concurrency controls dispatched group builds. Merge limits govern how many PRs land together, **not** how builds are combined. With “only merge non-failing pull requests” disabled, a group may include a PR whose required checks failed if the last PR's combined group passes. GitHub's successful two-PR example says the second temporary group is merged to the target. These statements do not specify a universal equality theorem for every intermediate landing tree. Source: [queue settings and examples](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).
- Ordinary GitHub merge methods differ: merge creates a merge commit, squash combines commits, and rebase creates new commit SHAs. Queue settings choose the method; repository-wide allowed methods do not identify the queue's selected method. Source: [pull request merges](https://docs.github.com/en/pull-requests/reference/pull-request-merges).
- A privileged administrator may bypass branch protections if allowed. Indirect merges can mark a PR merged even if that PR's protections were not satisfied. Sources: [queue usage](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request-with-a-merge-queue#adding-a-pull-request-to-a-merge-queue), [indirect merges](https://docs.github.com/en/pull-requests/reference/pull-request-merges#indirect-merges).

## Repository observations

Read-only `gh api` on 2026-10-28 UTC for `iqbal-codes/labq-software-factory` returned a private repository, default branch `main`, and `allow_merge_commit`, `allow_squash_merge`, and `allow_rebase_merge` all true. `GET /repos/iqbal-codes/labq-software-factory/branches/main` returned `protected:false`, `protection.enabled:false`, and empty required-check lists with enforcement `off`. This is the branch response, not proof of all applicable rules or bypass permissions.

The correct endpoints `GET /repos/iqbal-codes/labq-software-factory/branches/main/protection`, `GET /repos/iqbal-codes/labq-software-factory/rulesets`, and `GET /repos/iqbal-codes/labq-software-factory/rules/branches/main` each returned **403**, with GitHub's message: “Upgrade to GitHub Pro or make this repository public to enable this feature.” An initially attempted incorrect `branches/main/rules` path returned 404 and is not evidence about configuration. Thus effective rulesets, required checks, queue settings, bypass actors and organization-level rules are **unknown**, not proven absent. [GitHub documents merge queue availability](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue) for public organization repositories or private organization repositories on Enterprise Cloud; availability here is not established by the API responses.

## Binding consequences [INFERENCE]

- Treat each group SHA, its tree, base/ref and membership as candidate-specific. A recreated group requires new applicable evidence; a successful check for an earlier group or PR head is not evidence for a different candidate. A trusted check must actually checkout and test the event SHA, and report against that SHA; event metadata alone does not prove what ran.
- Bind independent parent-wide review and the real black-box runtime receipt to the candidate or to a separately proven equivalent tree, alongside spec, PR/head, base, policy and trusted producer identities. Check producer authority, scope and non-bypassability; GitHub's check conclusion by itself does not prove those properties. Preserve the earlier note's runtime snapshot/setup and environment limits.
- Before treating a queue as a preventive final-tree guard, establish the actual enforced rules, permitted bypasses, queue method and batch semantics, and a documented or otherwise independently proven mapping from the tested candidate tree to the landing tree for the selected configuration. In particular, one passing last group does not by itself prove every intermediate PR state was independently tested and reviewed. If the mapping or authority cannot be established, hold rather than claim exact binding. A post-merge comparison detects a mismatch after landing; it is not preventive.

No workflows, network tests, PRs, tracker writes, holdout contents, evaluators, or configuration changes were made. This is documentation/API research, not validation of GitHub's runtime behavior or authorization to merge.
