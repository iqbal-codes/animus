## Child graph and integration: concrete alternatives

The following are **decision paths to evaluate**, not authorization and not established supported end-to-end implementations:

1. **No intermediate PRs:** after human approval of the parent and its graph, an authorized coordinator could serialize already-decided child work using `archon-implement` on an integration checkout, advance only on its `green` outcome plus independent checks, then create one final PR. [INFERENCE] This avoids intermediate PRs in the described implementation primitive, but Factory entry exposure, supported invocation, stable child targeting, independent child review, exact checkout/branch behavior and the boundary between a thin coordinator and prohibited duplicate scheduling all require explicit decisions and tests. A human can own sequencing rather than an automated coordinator if that satisfies the outcome and permissions; neither alternative is proven by the pinned loop.
2. **Intermediate PRs into an integration branch:** where the requirement permits them, explicitly targeted child PRs can be assessed using native PR and merge-queue mechanisms, with separate authority per write, then one final integration-to-base PR. [INFERENCE] This gives forge-visible review but is not literally one PR total, and child PR merge/closing semantics, branch protection, final whole-spec validation and instruction conflicts remain open. Decide if this interpretation is acceptable before designing it.
3. **Upstream-supported parent composition:** seek a documented upstream interface or agreed extension that owns graph and final candidate without a private fork or duplicate engine. None was identified in inspected pinned surfaces. A later upstream revision or maintainer statement is not evidence about the pinned revision until evaluated and adopted under change control.

In each path, define the parent membership snapshot and directed edges; reject cycles, missing or ambiguous children and unresolved dependencies. Distinguish a child being *closed* from its required changes actually being present in the integration branch. Factory intake requires closed prerequisites and considers body and comment declarations; native `workability` only blocks references present on its supplied open board. A policy that runs dependent children before final closure therefore needs an explicitly approved admission rule; simply bypassing intake is not equivalent. Parent-wide branch ownership, compare-and-swap or equivalent serialization, recovery after a lost worker, conflict handling and stale membership/base revalidation are still missing. Per-item claims are not a parent branch lock.

## Exact final candidate and independent gates

Record the parent graph and contract version, integration head **H**, destination branch and its resolved base **B**, and the actual tested merge tree or executable identity **M**. An authorized final PR must point at H against B; if either moves, invalidate affected evidence and re-evaluate, including changed files and protected paths. A review of H alone and a runtime report about an unrelated deployment do not demonstrate the same candidate. A clean merge-tree identity and deployed runtime identity need an explicit trustworthy mapping; `candidate_command` only proves what its project-owned probe actually measures.

Require independently produced runtime and review records for the whole final contract, separately from builder checks, with provenance, identity, verdict, evidence and authorization. Explicitly hold missing, malformed, stale, inconclusive, failed or mismatched records; workflow completion and console `PASS` strings are not evidence. Review must bind its contract, reviewed head and appropriate base/diff; runtime must bind M to the running target and establish cleanup and scenario secrecy. Merge queue can consume eligible evidence but optional evidence and a model assessment do not themselves enforce this project's required two independent gates. The selected gate also needs protected-path policy, CI/branch-protection facts, human approval and a fresh final readback; unknown protection, changed head/base or unconfirmed forge result holds. Establish which authority may create a PR, publish review, approve, merge and deploy separately.
