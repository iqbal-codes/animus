# Issue 55: synthetic CLI-to-server lifecycle and replay probe

## Result

A real local Archon server and a separate CLI process shared a disposable SQLite database. A synthetic bash-only workflow completed and its lifecycle reached a real dashboard SSE connection. **The same four lifecycle notifications were observed repeatedly:** each subsequent group started with `running` even after `completed` had been delivered. Run-detail HTTP returned the durable terminal state and four corresponding events. Provider-event HTTP returned an empty list; this workflow did not invoke a provider, so it is not a positive provider replay test. This does not resolve issue 55.

The prior setup and its constraints are in `cc0fd5c:docs/research/issue-55-synthetic-isolation-and-events.md`; prior source analysis is at `d239fa4:docs/research/archon-replay-deep-dive.md`. This experiment used the cached source at revision `5c4f5e484262185926b37b070457fabb9bfedae0`; `git status --short --untracked-files=no` reported no tracked modifications before copying. Untracked source files and dependency integrity were not independently audited. It is not an unmodified binary: only the copied `packages/core/src/services/run-live-owner.ts` owner directory was relocated from `/tmp/archon-<uid>` to `join(tmpdir(), ...)`, as in the prior setup. No external model, issue tracker, real workflow, or holdout content was used.

## Observations

- The server was launched directly via `startServer({port:43197, skipPlatformAdapters:true})`, with `HOST=127.0.0.1`, and returned HTTP 200 on `/api/health`. The server reported SQLite at the disposable `ARCHON_HOME/archon.db`, and its dashboard poller interval was 1,500 ms. Startup ran its immediate cleanup scheduler against the empty disposable database: zero environments and zero removals. It logged a `gh_auth.status_failed` warning; execution of the real `gh` binary was denied by the sandbox. Missing web distribution and missing copied app-default workflows were also logged; neither blocked the API probe.
- A first SSE connection timed out after three seconds before the CLI started, due to the **probe client's** read timeout. Nevertheless, the separate CLI returned 0 and the server's list endpoint showed its completed synthetic run. This first attempt is not evidence of lifecycle delivery.
- In the second attempt, the SSE client used a 20-second read timeout and connected before the CLI. The CLI ran `workflow run synthetic --cwd <disposable repo> --no-worktree --json`, printed `synthetic-ok` and completed with exit 0. The stream returned a heartbeat, then four notifications for run `357ab836-7df7-41c7-8bff-d713741bb979`: `workflow_status/running`, `dag_node/work/running`, `dag_node/work/completed`, `workflow_status/completed`. The completed status had an empty workflow name. This exact lifecycle sequence was observed **four times**, approximately 1.5 seconds apart, before the query; event timestamps were regenerated on each emission. Thus the observed stream is not monotonic and cannot itself be treated as a unique transition log. The repeated payloads carried the same node invocation and attempt identifiers. Cause was not independently established; `packages/server/src/adapters/web/dashboard-event-poller.ts:55-153` implements a timestamp cursor and boundary-ID deduplication, but source inspection alone does not establish which part failed here.
- `GET /api/workflows/runs/<id>` returned 200, status `completed`, and durable `workflow_started`, `node_started`, `node_completed`, `workflow_completed` records in event order 5–8; `node_completed.data.node_output` was `synthetic-ok`. `GET .../provider-events` returned 200 `{"events":[]}`; `?step=work&attemptId=unknown&afterSeq=0` also returned 200 and an empty list. No provider rows were created; neither nonempty replay nor a cursor boundary was exercised.
- A second dashboard connection after completion returned 200 and its first line was a heartbeat. The first connection remained active: this was an additional connection, **not** a disconnect-and-reconnect recovery test. No claim is made that missing lifecycle events are replayed or that the reconnect stream stays empty.

[INFERENCE] Consumers should treat these notifications as invalidation hints and reconcile run state, not blindly apply arrival order or count each notification as a distinct transition. This single local SQLite probe does not establish the scope or root cause of the observed repeated emissions.

## Isolation and cleanup

The canonical root was `/private/tmp/issue55-event.cAxHWrEX`; source and installed dependencies were copied there excluding `.git` and `.archon`, and a new empty Git repository held the sole `echo synthetic-ok` node. Server and CLI inherited an empty-environment allowlist with disposable `HOME`, `ARCHON_HOME`, and `TMPDIR`, system-only `PATH`, telemetry disabled, and loopback host. No provider credentials were supplied. Server startup uses a global-auth *sentinel* when no credentials are configured (`packages/server/src/index.ts:48-55`), but the workflow did not execute an AI node.

The macOS sandbox profile denied writes outside the root except `/dev/null`, denied the named factory holdout read, denied network by default, permitted loopback bind/inbound, permitted outbound TCP only to `localhost:43197`, permitted Unix sockets, and denied execution of the resolved real `gh`. Direct preflight showed: loopback bind/connect/byte exchange at that port succeeded; TCP to `1.1.1.1:443` and the unapproved `127.0.0.1:43198` failed with `EPERM`; a real-home write and holdout listing failed with `EPERM`; a disposable-home write succeeded; real `gh` execution failed with `EPERM`. The holdout was not opened. Apple's developer-tool wrapper printed an xcrun cache-write denial, but synthetic Git initialization succeeded and the workflow ran. These are sampled checks, not complete protocol or process containment. Unix sockets and reads outside the named holdout remain allowed, and path-specific `gh` denial does not cover copied binaries. Only the owned server endpoint was deliberately contacted; the profile is not a hostile-code boundary.

The supervisor started server and CLI in separate sessions, imposed bounded startup and CLI waits, sent SIGTERM to their owned groups, escalated to SIGKILL on timeout, and reaped both leaders. In the successful run both leaders exited 0; a targeted process listing found no remaining command containing the unique root. That listing and group cleanup do not prove absence of detached or renamed descendants. The supervisor itself and its HTTP client were outside the sandbox; its only HTTP target was the explicitly owned loopback endpoint. The disposable root was removed after the observation, and no production state or tracker was changed.

## Remaining gaps

Positive synthetic provider-event creation and HTTP replay, late or missing rows, multiple attempts, cursor boundaries, disconnect/reconnect recovery, saturation, isolated differing database identity, auth, safe transcript projection, cancellation and deployed topology remain untested. No WebSocket semantics are established. The observed repeat warrants a focused reproduction and root-cause investigation with controlled timestamps before attributing a defect to a specific implementation.
