# Issue 56: final integration evidence seam

## Conclusion

The pinned Archon and Factory contracts provide useful **pieces**, not a proven atomic final-integration gate. A current-head review, a verified runtime result, and passing PR checks do not by themselves establish that the exact tree ultimately merged was independently reviewed and black-box tested. The agreed boundary is **one PR total per spec**, proportionate child checks, and black-box validation of the integrated candidate only—not a black-box gate per child. This is research, not authorization to execute or a claim that issue 56 is resolved.

## Source-proven boundaries

### Review

- `.archon/workflows/sdlc/review/archon-review-block.yaml` declares `scope`, `work_order`, `part`, and `ready`; empty `part` means the whole contract, while a part can defer items. Scope checks PR head before the lenses; `mode` records checkout HEAD; synthesis returns `ready`, `contract_left`, and an artifact pointer. The graph says a selected failed lens must cause `ready:false`; the publish node may write a canonical PR comment. This is an agent-authored assessment; a fresh context or parallel lens alone does not establish independent organizational identity, complete immutable parent-spec coverage, or base/merge-tree binding. The gate should not treat `ready` alone as proof of those properties.
- Factory `factory/WORKFLOW_POLICY.md`, “Runtime and review evidence”, requires credible independent review, current PR head, ready verdict, and no unresolved blocking findings. It accepts a canonical report or an eligible external/human report; it does not make every canonical report automatically independent. `docs/agents/software-factory-workflow.md` distinguishes the builder and independent reviewer and rejects fabricated native evidence.

### Runtime and provenance

- `.archon/workflows/sdlc/verify-runtime/archon-verify-runtime.yaml` takes scenario and candidate; empty candidate checks report/probe agreement only. It returns `verified`, `verdict` (`verified`, `failed`, `inconclusive`), `candidate`, `checkout`, and report location. It is not itself a typed PR/head/base/merge-tree receipt. External environment ownership is required. A boolean or a path supplied by an untrusted producer is not provenance.
- `factory/RUNTIME_HOST.md`, “Bind the candidate root” and “Identity and supported shapes”, specifies committed included source from the delivering checkout at expected HEAD, a recorded revision/tree/resource digest, a fresh snapshot and state, and a target identity incorporating frozen bytes, launch configuration and allocation. Bound starts require expected revision; the target identity is not simply Git HEAD. The host reports source revision/tree/resource digest and input/source digests; configuration must include all executable application code. Setup can change snapshot bytes, so the relation from committed tree to tested bytes includes the trusted include list, setup, and post-setup digest. HTTP identity requires app cooperation, and chmod/rehash is not hostile same-user isolation. External services and hostile processes exceed the documented boundary.
- `factory/RUNTIME_HOST.md`, “Mutation evidence”, explicitly says JSON alone is not a signed receipt. Its calibration requires a verified baseline, a relevant fault caught, and a separate wrong-identity inconclusive control; unavailable controls are not success. Calibration is distinct from running private holdout scenarios. `factory/WORKFLOW_POLICY.md` requires runtime and holdout evidence for the delivered candidate; ordinary checks are not a substitute. Private scenario data remains outside builder access and public evidence.

### Merge and checks

- `.archon/workflows/sdlc/merge-queue/archon-merge-queue.yaml` accepts an explicit batch, optional evidence and configurable check/path policies. The gate in `scripts/merge-action.ts` requires assessment booleans `validation_verified` and `review_verified`, acceptable CI/path facts, and a valid plan. The assessment is agent-authored; evidence array presence and file hashing do not prove authorship, independence, semantic completeness or candidate binding. An empty array is not rejected by `sealEvidence`; hashes protect listed file bytes against later change, not the truth of their content. Preview is read-only; other modes can write.
- `scripts/ci-policy.ts` reads PR `headRefOid` and `statusCheckRollup`, falling back to REST check runs and statuses for that head. It extracts context names, not expected app identity, selects a same-name latest run, treats `success`, `neutral`, and `skipped` as passing, and records `{pr, head_sha, check, state}`. The source comments describe the rollup as head checks; this is not independent proof of which commit each particular GitHub job actually executed, whether it used a synthetic merge, or its producer identity. It does not record a base SHA or merge tree for each result. An explicit `required_checks` declaration may be `none`; inaccessible GitHub policies otherwise become unknown, while visible enforced names are combined with a declaration. These are Archon implementation facts, not a complete statement of GitHub ruleset semantics.
- `scripts/refresh-merge.py` re-reads live base branch and compares it with the approved plan's `base_sha`, verifies PR head and target branch and rejects certain merge states. `scripts/merge-action.ts` rechecks plan and evidence digests, then calls `gh pr merge --match-head-commit <head>` and reads back merged state and base. This has a **base TOCTOU gap**: the pre-write base read and the merge request are separate operations; the shown write passes a head precondition, not an expected base or expected tree. Readback confirms a merged PR, not equality of its actual resulting tree to the tested tree. The source does not prove a transactional base lock or GitHub merge-queue integration.

## Practical contract [INFERENCE]

1. Freeze the accepted parent spec and membership/coverage manifest, with version and digest; integrate admitted child changes on the single spec branch. Child checks remain proportionate and are not final black-box evidence. Create exactly one PR. Do not defer parent items via `part` at final review. Enforce the one-PR and separation-of-duty requirements through authority/credentials and records, not prompts.
2. Define qualified repository and PR, current head **H**, current destination branch and full base **B**, and a deterministic candidate **M** (commit plus tree digest and parents, or another explicitly specified merge result). Record merge method and algorithm. Prefer a trusted merge-queue/serialization mechanism that guarantees the actual landing tree equals M; establish its guarantees independently. If using the existing head-only merge operation, a re-read of B immediately before the call reduces but cannot eliminate the race. Post-merge tree comparison detects a mismatch too late to be a preventive gate; do not claim it prevents an untested merge. Squash/rebase commit IDs may differ even if trees match; require the intended tree and semantics, not assumed SHA equality.
3. Produce one parent-wide independent review bound to the frozen spec digest and H, and, where B affects reviewed changes, B/M or an explicitly reviewed equivalent tree. Require verified source and reviewer identity/authority, ready verdict, no unresolved blockers and empty contract-left. A head-only report cannot attest changed base content without a justified equivalence or renewed review.
4. Prepare the integrated candidate from an actual trusted checkout at M (or from H only if its tree is proven identical to M). Tie the Factory binding's revision, tree, include manifest and resource digest to M; capture trusted owner output, actual post-setup source digest and target identity, scenario/assertion revision, native run/attempt and result artifact digests. Require candidate nonempty and equal to the trusted current attempt identity, `verified:true` and `verdict:verified`, completed assertions and successful cleanup. Runtime and private holdout evidence must be independent as required by policy, scoped to the entire parent contract, and kept secret as applicable. A synthetic file or replay is not a native receipt. Factory's documented delivering-checkout/HEAD binding must be reconciled with any synthetic merge checkout before claiming this is supported.
5. Define required checks from a trusted policy snapshot, including check producer/app and acceptable conclusions. Record the **actual checked commit and tree**, event/workflow identity, status, and relationship to H/B/M; a check on H is not automatically a check on M. A merge-ref or queue candidate is usable only when its commit/tree and parents are independently established for this exact H and B. Do not silently treat skipped or neutral as substantive success unless the approved policy explicitly permits it. Unknown, missing, stale, ambiguous or untrusted facts hold.
6. At authorization, verify all evidence is authentic, independent, complete and consistently bound to the same PR/spec/H/B/M, plus approved protected-path policy. Invalidate on any relevant H, B, M, policy, spec, runtime or evidence drift; rerun affected checks and final black-box validation for the new integrated candidate. Use an enforceable atomic landing guard or a forge-native queue whose actual behavior is proven; otherwise hold. Separate publication, approval and merge authority.

## Unresolved proof and limits

- Offline source inspection establishes Archon's own reads and arguments, not GitHub's current check-run, merge-ref, merge-queue or branch-protection guarantees. GitHub primary documentation/API semantics and the actual repository configuration were not queried under the no-network constraint. In particular no claim is made that a PR rollup always identifies the tested merge commit, or that GitHub enforces a base compare-and-swap.
- The exact integration mechanism, immutable spec/graph authority, reviewer independence, trusted evidence storage and signer/attestation, environment ownership, accepted protected paths, runtime/holdout coverage, supported synthetic checkout integration, and atomic merge enforcement remain decisions or engineering work. A digest is integrity only when its binding and authority are trusted.
- Static inspection and local Git metadata only; no workflow, evaluator, test scenario, real `gh`, network, tracker write, or product change was executed. No evaluator or holdout content was modified. This note does not demonstrate a successful final gate.
