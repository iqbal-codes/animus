# Issue 56: pinned Archon checkout lifecycle and pre-node control

## Conclusion

The inspected CLI does **not demonstrate a caller-controlled pre-node verification barrier or exclusive filesystem ownership**. Its start observation is useful audit evidence, not an approval gate: a fresh run claims execution, samples its actual checkout, persists that sample before the first node, and continues without comparing it to a caller-supplied SHA. Factory can potentially prepare and verify a private checkout and dispatch with `--no-worktree`, but the safety of that design depends on independent, enforced control of every writer for the whole interval; the CLI flags and Git worktree lock do not establish it. No end-to-end Factory implementation or workflow execution was tested.

This extends `git show ead1f51:docs/research/issue-56-exact-child-dispatch.md`. Factory `factory/pack.json` pins Archon `5c4f5e484262185926b37b070457fabb9bfedae0`; the inspected local cache HEAD equals that SHA. Archon links below are pinned to that commit. Factory's current `apps/engine-host/src/native.ts:276-311` constructs an `archon-loop` dispatch, not an exact-child checkout admission API.

## Source-demonstrated lifecycle

1. [CLI option handling](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/cli.ts#L737-L825) separates `--cwd` from `--workflow-source`; `--no-worktree` conflicts with `--branch`, `--from` and `--base`. The [isolation decision](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/commands/workflow.ts#L2200-L2242) defaults fresh repo runs to worktree isolation, subject to workflow policy. [`archon-implement.yaml`](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/implement/archon-implement.yaml#L1-L39) has no `worktree` policy. For a fresh in-place run `workingCwd` starts as `cwd`; [the no-worktree branch](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/commands/workflow.ts#L2671-L2677) leaves it unchanged ([branch](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/commands/workflow.ts#L3174-L3178)). This is not isolation, and continuation/adoption have separate lane decisions.
2. With an explicit branch, the CLI [looks up an active environment](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/commands/workflow.ts#L2856-L2860) and [reuses a healthy checkout](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/commands/workflow.ts#L3054-L3114), ignoring `--from` with a warning; base ancestry verification is warning-only and errors are skipped. A branch name, health check, or requested start ref does not verify exact HEAD or cleanliness.
3. A newly created task checkout [synchronizes its canonical workspace first](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/isolation/src/providers/worktree.ts#L964-L1006), using [reset for managed clones and fast-forward for registered local repos](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/isolation/src/providers/worktree.ts#L1335-L1379). This can involve fetching; the current investigation performed none. A new task branch uses the specified `fromBranch` or remote/base; if the branch exists and `--from` is present it errors, whereas without `--from` it attempts `git branch -f` before adding the worktree. It [reads `HEAD^{commit}` after creation](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/isolation/src/providers/worktree.ts#L1738-L1804) for `cutFromCommit`. The source accepts a start-point string; it does not establish a supported CLI contract guaranteeing a raw SHA, nor protect a movable ref against concurrent updates.
4. `git worktree add --lock` carries a unique setup marker. [Setup](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/isolation/src/providers/worktree.ts#L940-L1055) initializes submodules, copies configured ignored files, refreshes the index and releases that lock before returning; failures are handled as described in source. The lock protects Archon's setup/adoption and cleanup protocol, not writes by arbitrary processes. Git hooks and setup itself can run before any workflow-node baseline; setup may involve external access. A cut-from commit is not a guarantee that the eventual working files are identical to that commit.
5. After lane resolution, [the executor](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/workflows/src/executor.ts#L2213-L2254) claims a pending run and samples the checkout. [The database claim](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/core/src/db/workflows.ts#L473-L510) is an atomic pending-to-running transition with resource-slot and destroyed-worktree checks; it is not an OS lock on the path or a universal same-checkout writer exclusion. After artifact setup, [baseline persistence](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/workflows/src/executor.ts#L2627-L2667) is fail-closed on persistence errors but accepts an `unavailable` observation. The [store](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/core/src/db/workflows.ts#L512-L534) makes the first recorded baseline write-once. Resume keeps the initial sample, not a new starting checkout. This is a sequence of observations and writes, not an atomic snapshot against external writers.
6. Detached acknowledgement supplies a run ID before the child has necessarily created its worktree (see prior note). Reading a persisted baseline later cannot stop a node that has already started. No public expected-SHA option, pause-after-sample handshake, or external approval callback was established by this inspection; absence here is an inspection conclusion, not proof that no internal extension could be written.

## Disposable Git probe

On the local machine, with no network, workflow, tracker, or Archon invocation, created a fresh temporary Git repository and an empty commit, then `git worktree add --lock --detach <lane> <sha>`. `git worktree list --porcelain` reported `locked added with --lock`. Writing an untracked file inside the locked lane succeeded, and an empty commit from that lane changed HEAD while the lock remained. This demonstrates that Git's administrative worktree lock is not a write/HEAD mutex in this local Git environment. It does not test Archon's own adoption logic or competing workflow runs. ## Candidate design and limits [INFERENCE]

- Factory could create a separate checkout at a resolved immutable commit, verify canonical repository identity, actual worktree path, symbolic/detached HEAD, full commit ID and required file state, then invoke a fresh `archon-implement` with that path as `--cwd` and `--no-worktree`, provided deployment actually exposes the entrypoint and policy permits it. `--from`, `--branch`, and `--base` cannot be supplied in that mode. The current Factory host does not implement this contract.
- A check immediately before process launch has a time-of-check/time-of-use gap. A cooperative mutex works only if **all** actors that can modify the checkout, Git administrative data and relevant refs obey it; a run ID, worktree lock, branch uniqueness or Archon resource claim alone is not proof of that. To claim exclusivity against noncooperating processes needs an independently enforced estate boundary and appropriate filesystem/credential controls, maintained through execution and recovery. The executing agent must be permitted to write its lane, so the boundary must distinguish authorized run activity from other writers. Repo identity, ignored files, submodules, hooks, config, and workflow source also affect the effective starting state; commit SHA alone does not certify all of it.
- To claim **verified before first node**, either verify the prebuilt checkout before dispatch while that independently enforced boundary stays intact, including the handoff into the actual execution context, or implement a supported synchronous fail-closed pre-node barrier that compares the actual checkout against the expected identity. No such barrier or estate is demonstrated here. The persisted baseline can corroborate after the fact, but mismatched, unavailable, absent, dirty or incomplete evidence must hold results; it cannot retroactively prevent execution. A matching observation is not proof of no intervening mutation.
- A robust design needs durable ownership, crash and orphan recovery, immutable expected SHA, revalidation of the actual execution path, controlled handoff and serialized compare-and-swap integration; document who can modify shared refs and how stale owners are fenced. Resume, reuse, adoption and separate Archon instances must not silently bypass the same rules. These are design requirements, not established features.
