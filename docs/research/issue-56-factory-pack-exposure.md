# Issue 56: Factory pack and installed entrypoint exposure

## Decision

**Do not treat `archon-implement` as an installed Factory pack entrypoint.** Factory's actual `factory/pack.json` is a Factory source-pin/catalog document, not an Archon `archon-plugin.json` workflow-pack manifest. The pinned Archon tree contains no workflow-pack manifest exporting this workflow. Source-mode discovery is a different mechanism and can find it, but Factory's current launch path explicitly runs `archon-loop`; neither fact establishes a supported Factory exact-child dispatch API. Keep issue 56 held pending a separately designed and verified admission/ownership and execution boundary. This extends `git show ead1f51:docs/research/issue-56-exact-child-dispatch.md`, including its one-PR and final integrated validation constraints.

## Evidence

- Factory HEAD `5fa30a37748d0acde86a6fc6c0fc3ba49d5e8105`, [`factory/pack.json`](../../factory/pack.json), pins Archon `5c4f5e484262185926b37b070457fabb9bfedae0`, sets `source_directory` to `.archon/workflows/sdlc`, and lists 12 human-described `entries`. `archon-implement` is not among them. Those `entries` are strings describing names, not Archon plugin `entrypoints` mapping names to workflow YAML paths. Default inputs are supplied only for loop, manager and holdouts. The pinned cache's `git rev-parse HEAD` returned the exact pin.
- The pinned tree's `git ls-tree -r --name-only HEAD` finds four `archon-plugin.json` files: `plugins/forge-github/archon-plugin.json` and `plugins/provider-{claude,codex,pi}/archon-plugin.json`. None is a Factory SDLC workflow-pack manifest. The implementation YAML exists at `.archon/workflows/sdlc/implement/archon-implement.yaml`. This is evidence about the pinned tree, not proof about any separate external installation.
- Archon's [`workflow-source.ts` lines 297–350](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/workflows/src/workflow-source.ts#L297-L350) reads `archon-plugin.json` from the installed receipt's commit tree and validates it as a workflow-pack manifest. [`workflow-discovery.ts` lines 947–1017](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/workflows/src/workflow-discovery.ts#L947-L1017) maps manifest paths to qualified `owner/plugin:<entrypoint>` names; other loaded workflows are support, not dispatchable. Internal `include:` composition can use support, but a `workflow:` child targeting support produces a validation error. A declared path that does not load also produces an explicit validation error. The pinned [`installed-packs.test.ts` lines 150–186](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/workflows/src/installed-packs.test.ts#L150-L186) specifies these catalog and resolution boundaries for a test pack; it is not a test of Factory's deployment.
- Factory's [`apps/engine-host/src/native.ts`](../../apps/engine-host/src/native.ts) lines 24–50 checks a local source directory or pin-named cache; lines 263–311 construct a CLI invocation using the cache root as `--workflow-source` and hard-code `archon-loop`. The status lookup's directory/hash is not a verification that the cache commit equals the pin. `.factory/consumer.json` is absent in this checkout. No live installed-pack receipts or deployment configuration were inspected, so installed-pack availability in another environment remains unknown.
- The earlier source discovery probe in `git show f1b1d6d:docs/research/spec-integration-entrypoint-followup.md` found `archon-implement` under isolated source roots but reported 21 provider validation errors and a dropped `mutates_checkout` warning. It used `providerRegistry` without CLI provider registration. Pinned CLI [`cli.ts` lines 131–160](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/cli.ts#L131-L160) registers built-in, community and installed plugin providers before normal routes. Consequently the earlier errors cannot be assumed to describe the configured CLI, and the successful discovery cannot establish that Factory's actual provider configuration is valid. Neither configuration was verified here.

## Offline non-executing schema probe

Used existing pinned cache dependencies and Bun to apply the pinned exported `workflowPackManifestSchema.safeParse` directly to the actual Factory `factory/pack.json`; no installation, workflow dispatch, nodes, holdout, tracker, or network request to a service. macOS `sandbox-exec` denied network and execution of `gh`; an attempted `gh --version` returned `/opt/homebrew/bin/gh: Operation not permitted` (exit 126); an outbound `nc` probe exited 1. The network probe does not distinguish sandbox denial from other connectivity failure. The schema result was rejected with:

- `schemaVersion`: `Invalid input: expected 1`.
- `name`: `Invalid input: expected string, received undefined`.
- `kind`: `Invalid input: expected "workflow-pack"`.
- `entrypoints`: `Invalid input: expected record, received undefined`.
- Root `unrecognized_keys`: `repository`, `integration_revision_required`, `source_directory`, `default_inputs`, `entries`, `launch_gates`, `capabilities`.

An initial attempt failed before parsing with `TypeError: Expected file path string or file descriptor` because `FACTORY_PACK` was not set; the successful invocation explicitly set it to this checkout's manifest. A separate first `gh` probe used nonexistent `/usr/bin/gh` and returned `ENOENT`; the subsequent probe above used the actual PATH resolution. These failures are not workflow validation outcomes. No actual installed-pack discovery or provider-configured integration probe was run.

## Practical consequence and next evidence

[INFERENCE] For installed-pack dispatch, an explicitly authored, validated, installed workflow-pack manifest would need to export an implementation entrypoint, and the resulting qualified name and full pack validation would need testing against the real supported configuration. Merely adding a key to Factory's `entries`, guessing a qualified name, or observing source discovery cannot produce that contract. This is not a recommendation to edit the manifest without design approval.

For source mode, a future non-executing, sandboxed integration probe should use the actual Factory runtime configuration and CLI-equivalent provider registration, capture all discovery errors and dropped fields, and verify the resolved source and exact workflow identity. It must not run workflows or read holdouts. Even a clean result would not settle admission, exclusive claims, the pre-node checkout barrier, credentials fencing, result verification, integration serialization or the single final PR; the prior note's fail-closed conditions still apply. Execution and publication require separate authorization.
