# Research: parent-spec integration and one final PR

## Verdict

**Not demonstrated at the pinned revision.** Archon exposes real per-dispatch base and worktree primitives, and separate runtime, review and merge-queue workflows. The inspected `archon-loop` is nevertheless a board-wide, one-item/one-PR loop, not a demonstrated parent-scoped integration orchestrator. Its explicit builder instructions start new issue work from the default branch, and its picker and claim protocol do not bind a lap to a requested child. A `--base` flag alone is therefore not proof of the requested end-to-end contract. No live workflow was launched. Issue [#56](https://github.com/iqbal-codes/labq-software-factory/issues/56) has no comments; its parent [#46](https://github.com/iqbal-codes/labq-software-factory/issues/46) excludes a private workflow fork and a duplicate engine, and reserves launch and publication to separate permissions.

**Critical current-repository risk:** the console's `readLapEvidence` returns hard-coded `verified`/`PASS`, `approved`, and `independent: true`, rather than deriving those facts from a run. It cannot establish final-PR evidence or review. See [native.ts:198–225](https://github.com/iqbal-codes/labq-software-factory/blob/5fa30a37748d0acde86a6fc6c0fc3ba49d5e8105/apps/engine-host/src/native.ts#L198-L225). This is an observed implementation fact, not evidence that a native run passed or failed.

## Observed native primitives and limits

### Dispatch, isolation and targeting

1. Archon CLI documents `--branch` as creating or reusing a worktree, `--from` as a start point, and `--base` as a per-dispatch override for epic slices (worktree cut-from and PR target) ([help.ts:628–656](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/help.ts#L628-L656)). The command threads the override into both isolation and workflow execution ([workflow.ts:2187–2188, 3140, 3345](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/commands/workflow.ts#L2187-L2188)); its unit test explicitly checks both channels ([workflow.test.ts:4319–4375](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/commands/workflow.test.ts#L4319-L4375)). Existing branches/worktrees and stale bases still require explicit reconciliation; a flag is not a serialization lock.
2. `archon-loop` inputs list runtime, protected paths, merge, attempt/rejection limits, deployment and claim lifetime, but no parent, child target or integration branch ([archon-loop.yaml:19–66](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/loop/archon-loop.yaml#L19-L66)). Its picker chooses a route and target from the board ([lines 68–90](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/loop/archon-loop.yaml#L68-L90)); the builder says to use a PR branch or a **new branch from the default branch** and open a PR closing the issue ([loop-work.md:23–33](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/loop/commands/loop-work.md#L23-L33)). [INFERENCE] The CLI's generic base support cannot by itself override those agent instructions or guarantee the picker chooses a specified child.
3. Factory's `launchNativeLap` constructs a unique `archon/lap-*` branch and passes `merge=approve`, default inputs and an unstructured specification, but no `--base`, parent or deterministic child ([native.ts:246–309](https://github.com/iqbal-codes/labq-software-factory/blob/5fa30a37748d0acde86a6fc6c0fc3ba49d5e8105/apps/engine-host/src/native.ts#L246-L309)); its HTTP handler passes only `specification` ([main.ts:83](https://github.com/iqbal-codes/labq-software-factory/blob/5fa30a37748d0acde86a6fc6c0fc3ba49d5e8105/apps/engine-host/src/main.ts#L83)). `merge=approve` leaves merging to a human, not the native auto land gate ([archon-loop.yaml:39–43](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/loop/archon-loop.yaml#L39-L43)).

### Dependencies and claims

- The native scheduler's pure `workability` reads `Depends on:` issue-body references and blocks dependencies present in the supplied open board; it considers `needs-owner`, active claims and PR references, but not Factory's `ready-for-agent`/`needs-info` labels ([workable.ts:64–72, 106–165](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/.shared/workable.ts#L64-L72)). It does not establish that a missing issue is closed. Factory intake instead parses body **and comments**, and holds missing or non-closed prerequisites and requires canonical readiness ([intake.ts:229–252, 316–384](https://github.com/iqbal-codes/labq-software-factory/blob/5fa30a37748d0acde86a6fc6c0fc3ba49d5e8105/apps/backend/src/intake.ts#L229-L252)). These are different gates; do not treat a native direct invocation as inheriting Factory admission.
- A claim is per work item: pick avoids live claims and overlapping areas as an instruction; the claim script posts and rereads, with the oldest live claim winning ([loop-pick.md:20–34](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/loop/commands/loop-pick.md#L20-L34), [claim.ts:21–52](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/loop/scripts/claim.ts#L21-L52)). Release only edits the run's own claim ([release.ts:2–32](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/loop/scripts/release.ts#L2-L32)). [INFERENCE] This does not provide a parent-wide integration-branch write lock; two distinct children may be claimed concurrently. An integration strategy must independently ensure serialized branch advancement, conflict handling, and stale-snapshot revalidation without claiming this is native claim behavior.
- A single PR referencing several open children affects selection: native workability maps referenced issues to the PR and considers linked claims ([workable.ts:76–85, 139–165](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/.shared/workable.ts#L76-L85)). [INFERENCE] Reusing one PR for multiple unfinished children can cause the picker to continue that PR instead of picking individual issues; child completion/closure semantics need an explicit design.

### Final candidate and gates

- `subject` resolves a PR and records its forge base, head and changed files ([subject.ts:25–55](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/loop/scripts/subject.ts#L25-L55)). The app-check instructions checkout that head and test a detached merge with the passed PR base, report `merged_with`, and keep evidence outside the repository ([loop-check-app.md:70–76, 96–98, 114–124](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/loop/commands/loop-check-app.md#L70-L76)). The graph wires subject → independent app check → evidence → review → land ([archon-loop.yaml:146–151, 181–198, 227–247](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/loop/archon-loop.yaml#L146-L151)).
- Land verifies the PR head against reviewed SHA, checks the tested tree and PR base movement, can make a narrowly permitted clean base merge, and uses `gh pr merge --match-head-commit`; it refuses unsupported records ([land.ts:94–150, 163–180](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/loop/scripts/land.ts#L94-L150)). Reviewer instructions also discuss default-branch ancestry ([loop-review.md:93–96](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/loop/commands/loop-review.md#L93-L96)). The code uses the actual PR base; those instructions' default-branch language must not be assumed equivalent for an integration-target PR. Each head/base change needs fresh applicable evidence; no individual child result proves the combined final candidate.
- `archon-merge-queue` is a separate supported explicit-PR interface: up to five URLs, preview/approval/auto modes, optional evidence and protected paths, CI/path policy, assessment and pinned-plan approval ([archon-merge-queue.yaml:1–38, 130–161](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/merge-queue/archon-merge-queue.yaml#L1-L38)). It is not evidence of parent orchestration, nor automatically equivalent to the loop's independent black-box check and land gate. Standalone runtime verification and review are listed in [pack.json:22–30](https://github.com/iqbal-codes/labq-software-factory/blob/5fa30a37748d0acde86a6fc6c0fc3ba49d5e8105/factory/pack.json#L22-L30); their composition into a final-PR gate was not demonstrated.

## Decision paths, not authorization

1. **Seek an upstream-supported parent-scoped extension** that binds parent, child, base, branch ownership and final PR while preserving native review and merge gates. Confirm against upstream maintainers or executable contracts; no such complete extension was established here.
2. **Evaluate a supported external composition** using native isolated worktrees, explicit PR/review/runtime interfaces and merge queue, with an independently specified integration coordinator. Establish whether this violates #46's prohibition on a duplicate scheduler/engine; do not assume it is permitted. A sequence of child PRs into an integration branch plus a final PR is not literally one PR total, so clarify whether “one final PR” permits intermediate PRs and how children are closed.
3. **Retain normal per-item loop delivery** if a human changes the outcome requirement; it does not satisfy the one-final-PR contract as currently stated.

Before any execution, settle target selection and scope enforcement, dependency closure versus integration presence, parallel conflict policy and branch authority, recovery after a crash or lost claim, external writes/forge consistency, integration and final base movement, exact final candidate evidence, protected paths and holdout fencing, approval authority, and branch protection. Fail closed on unknown/stale/missing inputs. Do not use the console's current evidence projection as authority. Parent/child publication, launch, merge and deployment each need separate authorization.

## Offline behavior check and gaps

**PASS:** with `bun -e`, imported the pinned pure `workability` and `dependencies` functions and passed a fabricated in-memory board: open #1 blocked #2; missing #999 did not block #3; `needs-info` did not block #4; parsing `Depends on: #1, #2` returned two references. Output was workable `[1,3,4]`, waiting `[2]`; no network, workflow, forge writes, or holdout access. This probes the pure scheduler predicate only, not the model picker, Factory admission or an actual concurrent claim race.

**NOT RUN / unresolved:** full workflow integration; actual `--base` behavior with loop agents and existing worktrees; deterministic selection and parent isolation; upstream extension discovery beyond inspected code; final PR runtime/review/merge composition; crash, race, branch protection and moved-base scenarios. A controlled offline fixture suite with injectable forge and runner, exact head/base assertions, competing claims, missing dependencies and false/stale evidence should precede any authorized real execution. This research does not establish a safe supported complete one-final-PR workflow.
