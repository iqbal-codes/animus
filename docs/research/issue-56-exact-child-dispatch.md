# Issue 56: exact-child dispatch at the pinned Archon seam

## Conclusion

**`archon-implement` is a directly runnable, documented intent-to-commits workflow in the pinned source, not an exact-issue admission or ownership API.** The public CLI can name it without invoking `archon-loop`'s picker; its `work` input can carry an admitted child's frozen contract. This is a plausible execution building block, not proof that an agent executes only that child, that Factory exposes it, or that the one-PR coordinator is safe. User direction for this investigation is one PR total per spec, proportionate child checks, and black-box checks only on the final integrated candidate. This note does not authorize execution or close issue 56.

## Dispatch, binding and inputs

Fresh runs resolve a discovered workflow by name; they capture its source, and validate declared inputs before detach, worktree or AI execution ([resolution and gate](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/commands/workflow.ts#L1850-L1914), [gate](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/commands/workflow.ts#L2252-L2278)). `--workflow-source` cannot accompany resume or container; resume keeps captured source and original inputs. The current Factory host specifically dispatches `archon-loop`, not this entry ([host](https://github.com/iqbal-codes/labq-software-factory/blob/5fa30a37748d0acde86a6fc6c0fc3ba49d5e8105/apps/engine-host/src/native.ts#L246-L311)); Factory's pack entries do not list `archon-implement`. Source-mode discovery in the prior note is not evidence of installed-pack entrypoint exposure.
- [`archon-implement`](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/implement/archon-implement.yaml#L1-L39) describes itself as implementing decided work, committing without opening a PR, with one declared input `work`, default empty; it returns node `implement` with authored boolean `green`. The [deliver composition](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/deliver/archon-deliver-block.yaml#L100-L110) also includes it. This supports direct use as an Archon workflow in a discovery configuration where it is available; it does not establish a Factory host API or supported installed-pack export.
- Crucially the [implement command](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/implement/commands/implement.md#L1-L31) receives **both** `$INPUTS.work` and `$ARGUMENTS`; the operator message wins conflicts. Empty `work` does not prevent dispatch. A named issue prompts reading its current content and linked items: a frozen description alone does not force the agent to ignore later tracker state. The command instructs no PR or comment and no push unless work orders it ([instructions](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/.archon/workflows/sdlc/implement/commands/implement.md#L100-L117)); these are agent instructions, not a demonstrated capability sandbox. Neither claim, membership, dependency, exact issue identity, nor one-PR enforcement is a schema field.
- CLI strings split on the first `=`, allow empty values and reject duplicates, invalid names and unknown declared keys. A declaration's `required`, `default` and `description` do not validate work's semantic content ([input parser](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/workflows/src/workflow-inputs.ts#L1-L25), [resolution and grammar](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/workflows/src/workflow-inputs.ts#L70-L177), [schema](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/workflows/src/schemas/workflow.ts#L145-L153)). Defaults are applied by the executor; the top-level resolver validates but persists supplied values rather than materializing defaults ([resolver](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/workflows/src/utils/workflow-requirements.ts#L230-L270)).
- The public HTTP route `POST /api/workflows/{name}/run` accepts `conversationId`, nonempty `message`, and optional `inputs`, config and model overrides; input values must be strings, and the same declaration gate applies ([route](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/server/src/routes/api.ts#L914-L932), [input parser](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/server/src/routes/api.ts#L1830-L1857), [handler](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/server/src/routes/api.ts#L3463-L3508)). It returns an acceptance, not a completed child. No supported Factory SDK method for exact-child dispatch was established; exported `@archon/workflows` modules are engine modules, not evidence of a stable external coordinator SDK ([exports](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/workflows/package.json#L1-L45)). ## Identity and result

- CLI worktree isolation defaults on for git projects, unless policy or flags change it. `--branch` is mutually exclusive with `--no-worktree`; `--from` determines fresh cut-from and `--base` the PR base. An existing healthy branch worktree can be reused, ignoring `--from`; its base check warns only ([CLI](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/cli.ts#L749-L825), [creation/reuse](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/commands/workflow.ts#L3039-L3114)). A branch label or requested `--from` is not proof of actual SHA. The persisted run exposes `working_path` and `checkout_baseline`, observed after execution claim and before the first node; baseline may be absent or unavailable ([schema](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/workflows/src/schemas/workflow-run.ts#L271-L324)). This observation alone is not a pre-execution lock or proof that the lane cannot change concurrently.
- `--detach --json` returns a launch acknowledgement with `runId`, not the verdict ([ack](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/commands/workflow.ts#L2597-L2627)). `workflow wait --json` reports attention/deadline/owner-loss, with deadline exit 3; exit 0 is not green ([wait](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/commands/workflow.ts#L4400-L4457)). `workflow get --json` exposes the persisted run, terminal record and optionally node details; missing record/events fail ([get](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/commands/workflow.ts#L4892-L4990)). `green: false` maps to authored outcome `failed`, independently of terminal status ([executor](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/workflows/src/dag-executor.ts#L11590-L11610)); a successfully completed workflow can therefore have failed authored outcome. Synchronous execution can also return normally while paused or when outcome lookup is unavailable ([terminal logic](https://github.com/coleam00/Archon/blob/5c4f5e484262185926b37b070457fabb9bfedae0/packages/cli/src/commands/workflow.ts#L3555-L3630)). Never equate process exit, acceptance, wait success or `completed` alone with green.

## Practical fail-closed contract [INFERENCE]

1. The approved Factory coordinator—not the loop picker—must own a durable, versioned graph/admission snapshot, exact repository-qualified child identity and immutable work contract, dependency decisions and exclusive claim, with recovery rules. Verify current admission and ownership immediately before dispatch; stop on ambiguity, drift, duplicate claim or changed dependencies. The approval of a coordinator does not itself settle how to change existing closed-dependency admission semantics.
2. Resolve the pinned source and actual supported entrypoint in the deployment mode; reject wrong source digest, duplicate/ambiguous discovery, missing configured providers or dropped safety-relevant fields. Submit one nonempty frozen `work` value and a nonconflicting operator message, capturing both and their digest. Verify the selected workflow and returned run ID; no implicit loop selection. Agent instructions and untrusted tracker text are not a deterministic enforcement boundary; prevent unauthorized PR/comment/push through separately enforced credentials/capabilities, not prompt alone.
3. Exclusively control the integration lane, verify repo, actual checkout path, branch and exact starting commit before first node, and corroborate the persisted baseline. Refuse reuse or adoption without equivalent verified identity and exclusive ownership. Serialize integration with compare-and-swap against the expected head; stop on conflicts, unknown state, unclean worktree or changed base. **[INFERENCE]** The observed baseline is after the run claims execution, so this seam alone does not provide a caller-controlled pre-node verification barrier; a safe barrier or independently enforced estate is still required.
4. Require terminal `completed` **and** persisted authored `outcome: succeeded`, matching run/workflow/input/checkout identity, clean expected commits and proportionate child checks. Missing, paused, failed, cancelled, stale, unreadable or inconsistent evidence is a hold. Inspect changes against the child contract; `green` is agent-authored, not proof of correct scope or checks. Do not publish a child PR.
5. After all admitted child changes are integrated, create exactly one spec PR under separate authority. Bind final review, required checks and the one black-box validation to the exact integrated head H, base B and tested merge candidate M, including runtime identity; invalidate on drift. Missing or inconclusive parent-wide evidence holds. Child-focused checks are not substitutes for final integrated validation; do not run child black-box gates.

## Remaining decisions and authorization

The user's direction settles one total PR and where black-box checks occur, not graph snapshot/membership authority, dependency treatment for still-open siblings, exact claim and serialization mechanism, failure recovery, credential/capability fencing, reviewer independence, protected paths, or H/B/M-to-runtime identity. Establish these before implementation or execution. Confirm source-mode versus installed-pack availability with the real configured provider registry and a non-executing integration test; verify a safe pre-node estate barrier and exact result mapping. Separately authorize actual workflow execution, PR publication, deployment and merge. No such actions occurred here.
