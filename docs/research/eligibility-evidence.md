## Observed: admission versus selection

- Factory's policy requires an open issue with `ready-for-agent`, no blocking/exclusion labels or active claim, and closed, verifiable prerequisites (`docs/agents/software-factory-workflow.md:53-64`). Planning-only records are held; this applies to Wayfinder research, prototype, grilling, and map records unless explicitly published as executable work, not merely to their `wayfinder:*` label (`docs/agents/issue-tracker.md:31-38`; `docs/agents/software-factory-workflow.md:55-63`). Native edges and textual dependency lines must agree (`docs/agents/software-factory-workflow.md:45-49`).
- Intake parses body **and comments**, extracts all digits from a dependency clause, treats missing/non-closed prerequisites as unsatisfied, and checks the canonical labels and claim (`apps/backend/src/intake.ts:42-55, 206-249, 297-409`). Claims are recognized by a matching comment without inspecting expiry or completed run (`apps/backend/src/intake.ts:59-67`), unlike Archon's expiry and ended-run handling (`A:.shared/workable.ts:90-136`). These are not interchangeable representations.
- The pinned scheduler's workability calculation considers open issues and PRs, `needs-owner`, linked PRs, live claims, manager titles, and dependencies present in its open board; it has no canonical readiness test (`A:.shared/workable.ts:57-72, 108-166`). An unavailable, missing, omitted, or already closed referenced item is not in the open set and consequently is not a blocker in that calculation; this alone does not establish what the model picker will decide. The command tells the picker to read open issues (limit 200), continue eligible-looking PRs first, otherwise select issues based on priority/dependencies, and skip `needs-owner`, but does not require `ready-for-agent` or skip Factory's other hold labels (`A:loop/commands/loop-pick.md:7-13, 18-41`). It can write contract comments or labels and do bookkeeping before selection (`A:loop/commands/loop-pick.md:43-45, 69-75`). A planning ticket is therefore not protected merely by its Wayfinder classification. This is a source-backed risk, not proof a particular live agent would choose it.
- Workability also treats open PRs as independent workable items, including PRs linked to held issues except for `needs-owner` (`A:.shared/workable.ts:138-152`); admission needs an explicit policy for continuation as well as new issue starts. A check only on the initial issue route leaves this branch uncovered.
- Launch submission is only `{specification}` (`packages/contracts/src/operator.ts:95-100`); backend forwards it (`apps/backend/src/main.ts:151-169`), and host invokes detached `archon-loop`, passing that text after `--`, without an admitted issue identity or revalidation (`apps/engine-host/src/native.ts:246-310`). Pinned workflow inputs and pick node do not define a target input; `target` is **output** of the model pick and is then passed to claim/build (`A:loop/archon-loop.yaml:18-43, 70-103`). Consequently the submission text is not an enforceable bound target. The native picker can perform writes before a later claim or external post-pick check.

## Observed: intake scope and unknown states

- The backend constructs `new IntakeService()` without configuration (`apps/backend/src/main.ts:23-26`); its default is `labq-software-factory`, with bare repo names hard-prefixed to `iqbal-codes/` (`apps/backend/src/intake.ts:416-445`). Although the class accepts a repo option, the running endpoint does not pass the product repository. [INFERENCE] A different product checkout can therefore display the factory backlog while native `gh` selection acts in the checkout's repository; no cross-repository equivalence or mismatch guard is established by these code paths. Identity should include owner/repo, not issue number alone.
- Fetch is `gh issue list --state all --limit 100` (`apps/backend/src/intake.ts:440-452`); only those returned issues are evaluated, and missing dependencies are held (`:235-249, 487-497`). A closed prerequisite beyond that window can be falsely held, and `GET /intake/:number` returns 404 if absent from this bounded cached list (`apps/backend/src/main.ts:209-231`), not necessarily absent from GitHub. The 60-second cache (`apps/backend/src/intake.ts:424-430, 481-485`) cannot establish current admission at execution time.
- For valid-looking lap IDs, `readLapDetail` catches `native_state_unavailable` and searches an empty list, returning `lap_not_found`; host converts that to 404 (`apps/engine-host/src/native.ts:171-187`; `apps/engine-host/src/main.ts:201-216`). Even successful listing is limited to 100 runs (`native.ts:133-153`), so absence there is not definitive. Malformed IDs are independently rejected. Unknown/unavailable or truncated history must not be represented as authoritative nonexistence.

## Observed: evidence and report

- `readLapEvidence` returns `verified`, `PASS`, holdout `PASS`, review `ready`, `approved`, `independent: true`, a fixed reviewer session and zero findings regardless of actual events; head is the list projection's `checkout_baseline?.commit`, possibly null (`apps/engine-host/src/native.ts:147-159, 195-229`). No authoritative run evidence is consulted. It also claims report availability even when the report does not exist; `readLapReport` separately searches paths and can return `report_unavailable` (`native.ts:232-243`). Existing `tests/integration/evidence.test.ts:4-16` exercises malformed ID and a standalone string replacement, not a real evidence projection or redaction path.
- Pinned workflow records structured `subject` PR/head/base, `check-app` PR/head/merged-with and typed lines, deterministic `evidence.ok`, and fresh-context `review` with SHA/outcome/dispositions (`A:loop/archon-loop.yaml:149-169, 180-249, 267-309`). It feeds evidence to reviewer and merge gate; this is distinct from a successful ordinary test (`factory/WORKFLOW_POLICY.md:31-44`). A review result's head and outcome are useful but do not by themselves establish reviewer independence or the live PR head. Need provenance, event ordering/attempt association, fresh current candidate identity, actual report existence, and verified independent reviewer attribution before a ready projection. Do not infer a PASS from absent lines, null identities, a builder assertion, or merely a completed run. Keep private scenario content out of the projection.
- Host returns report as Markdown (`apps/engine-host/src/main.ts:189-200`), but backend `forwardToHost` unconditionally parses JSON before returning any success (`apps/backend/src/main.ts:29-61, 173-178`). Ordinary Markdown therefore becomes `502 invalid_host_response`; valid JSON text would instead be reserialized as JSON. Client expects text (`packages/client/src/index.ts:179-208`). `report_unavailable` is also absent from `operatorErrorSchema` (`packages/contracts/src/operator.ts:9-30`); client report handling accepts arbitrary error strings rather than validating the schema. Report-path behavior and error types need an explicit contract, including unavailable versus not found.

## Decision constraints and candidate approach [INFERENCE]

1. Establish a single authoritative, deterministic admission decision on the **actual execution path**, scoped to a verified repository and explicit issue/PR identity; re-read complete authoritative prerequisite, labels, claims and current state at the decision point. An old cache, prompt instruction, UI result, or reference in specification is insufficient. Missing, inaccessible, truncated, contradictory, or unsupported evidence must hold, not admit. Native GitHub dependency edges and textual declarations must be reconciled, including comments and planning-only records.
2. Bind the admitted identity to the work actually selected and claimed, including continuation of linked PRs. Address the check-to-claim race and revalidate after claim and immediately before any work or other selection-side effect. Deny on mismatch or loss of claim. Because the pinned workflow has no target input and its picker can write before claim, a pre-launch wrapper alone cannot establish this property; changing the engine/workflow would require separate authorization and a verified integration revision. Until an approved authoritative seam exists, hold launches where this guarantee is required. Direct native invocations and scheduler paths must not silently bypass the eventual control.
3. Derive evidence from authoritative completed native run events/artifacts for the exact attempt, candidate PR/head and current identity; validate chronological consistency and reviewer provenance independently of the builder. Fail closed on missing, stale, mismatched, partial, rejected, unverified or ambiguous evidence. Expose only allowlisted metadata, not private evaluation content. Do not alter the evaluator or its acceptance criteria to make the projection pass.
4. Resolve the actual native run store and report artifact formats before specifying adapters; distinguish authoritative absence from inaccessible state and limited lists. Proxy Markdown as text, preserving safe content type and typed error semantics; test the entire host→backend→client path.

Recommended offline regression coverage, once implementation is separately authorized: (a) unlabeled, each hold/exclusion, planning records, unknown/closed/open prerequisite, comment dependency, native-edge disagreement, expired/live claims and competing claims; (b) PR continuation linked to held issue, cross-repository same number, selector mismatch, race and direct launch bypass; (c) source-unavailable versus genuinely absent, >100 records and pagination failures; (d) absent/failing/stale/cross-attempt/null-head evidence, changed PR head, self-review and unresolved findings, positive independently attributed current-head case; (e) real Markdown through host/backend/client, JSON errors and missing reports, preserving privacy. Use injectable offline transports and synthetic artifacts; never inspect real holdout scenarios.

## Unresolved gaps

- Native run event schema, session attribution guarantees, artifact locations, and fresh forge-head lookup were not fully traced or exercised; the workflow's schemas alone do not prove a usable independent-review provenance chain. No live workflow or forge mutation was attempted.
- Product repository configuration and desired cross-repo authority need an explicit owner decision. Native edge and text conflict policy, linked PR continuation, historical comments, and claim expiry reconciliation need agreed semantics.
- Static report/unknown-state findings were not exercised end-to-end: tests require dependencies and an isolated host/backend fixture. No claim is made that the issue is resolved.
