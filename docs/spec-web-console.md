## Source and problem

The operator needs one console to register multiple GitHub repositories, prepare a structured backlog, execute work that is actually authorized, observe processes and evidence, and control approval and delivery without switching to a shell for every operation. Project scope must remain correct throughout the flow, including when multiple tabs open different projects.

The map settled the architectural direction, not its implementation. The map and child-issue closure notes do not prove that the pinned engine's capabilities are safe. The research resolutions for [live events and run controls](https://github.com/iqbal-codes/animus/issues/55#issuecomment-6461315841), [one-final-PR delivery](https://github.com/iqbal-codes/animus/issues/56#issuecomment-6460939033), and [eligibility/evidence integrity](https://github.com/iqbal-codes/animus/issues/57#issuecomment-6461209829) explicitly state negative or unproven findings. Their proof obligations are carried into this spec, not considered complete because the research was closed.

Research notes at older commits still mention open tickets. For planning disposition, the latest resolution comments are the current source; the technical limits and probe results in the notes remain applicable. Those probe results are historical evidence, not tests rerun during this specification session.

## Outcome

One single-host, single-tenant, local-first application lets the operator manage isolated GitHub projects through structured actions from spec/backlog intake to delivery. Web and backend are available on one localhost origin; a private engine-host bridges to pinned Animus. The installation may be exposed on a private network only after access configuration and authenticated operator identity have been proven.

A spec with subtickets produces exactly one final PR from the integrated candidate. A standalone ticket produces its own single PR. The operator can leave authorized execution running unattended, but every gate, permission boundary, and repository policy still applies. The UI honestly displays sources, freshness, limitations, and partial effects.

Unproven capabilities must be held. Displaying `unsupported` or `unknown` fulfills the honesty obligation for that capability, but **does not replace required outcomes** such as safe admission, project isolation, and final-candidate delivery. If the permitted engine seam cannot meet an outcome, the spec remains blocked and requires an operator decision, not a silent scope reduction.

## Invariants

1. **One owner of truth.** GitHub owns repositories/issues/PRs and forge state; Animus owns execution/workflow state. The console owns the registry, non-secret configuration, command ledger, and agreed spec-delivery coordination. Projections/caches can be rebuilt and do not replace the original authority.
2. **Explicit scope through to effects.** Project-specific queries, commands, subscriptions, runs, evidence, approvals, schedules, and promotions are bound to a verified project ID and resource. Missing/unknown/mismatched scope is rejected without falling back to the CWD, last project, or default repository.
3. **Admission precedes execution effects.** Planning records, held/excluded issues, unverified targets, and unmet prerequisites must not cause selection/claim/execution side effects through direct, scheduled, continuation, or spec-coordination paths. UI labels and prompts are not enforcement boundaries.
4. **Separate permissions.** Publication, admission, launch, approval, merge, promotion, and deployment are distinct permissions. Auto-merge and auto-deploy are independent project policies. Network membership, an accepted request, or a historical gate does not grant additional authority.
5. **Candidate-bound evidence.** Runtime checks, independent review, and landing decisions apply to the same candidate and relevant base/merge tree. Stale, incomplete, non-independent, or unverified evidence holds readiness/merge. Builders do not certify their own results.
6. **Protected secrets and evaluator.** Credentials, private holdout, and raw privileged data do not enter the browser, console DB, command history, logs, reports, or operator projections. Ordinary tests must not replace independent evaluation. The implementation must not weaken the evaluator/governance or create a private workflow fork to bypass boundaries.
7. **External effects are not a single transaction.** A persisted request, acknowledgement, completion, and verified outcome are distinct. A timeout does not prove the absence of effects. Reconciliation precedes consequential retries; there is no exactly-once claim across GitHub/Animus.
8. **Clean cutover per feature.** Each contract change atomically migrates all related feature callers, without shims/aliases or permanent parallel implementations. Unmigrated features remain explicitly active legacy, rather than being claimed to follow the new architecture.

## Acceptance criteria

The following criteria define the target executable contract.

### Projects, data, and recovery

- [ ] **AC01: Verified registration.** The operator can select a local Git checkout, clone a GitHub repository, or create a GitHub repository with a checkout. All three paths verify the GitHub host + stable repository ID, checkout, and operator choice before activating the project. Each repository has only one active project per installation. A rename/transfer with the same ID preserves identity; unverified addresses are not considered equivalent. Test all three paths, duplication, offline behavior, and mismatches.
- [ ] **AC02: Partial registration effects and retargeting.** Create confirms the owner, name, visibility, and checkout location. An already-created repository or partially cloned folder is reported if a later stage fails; it is not automatically deleted. A missing checkout or changed checkout identity holds related operations. Changing the checkout for the same repository requires explicit selection/validation; a different repository requires a new project. Test failures after effects and retargeting to the wrong repository.
- [ ] **AC03: Cross-project isolation.** Two projects with similar issue/run numbers do not affect each other through queries, commands, evidence/reports, schedules, controls, promotions, or subscriptions. Tab A continues targeting A when another tab opens B. Access to run B through A is rejected. Unknown/missing scope produces a classified refusal without effects. Aggregates display project provenance and open correctly scoped details. Prove this in the backend and host, not only the browser.
- [ ] **AC04: Durable registry and commands (WAL SQLite & Single Writer).** Console-owned SQLite resides in an isolated installation state directory (`~/.factory/state/console.db` with 0700 permissions). WAL mode is active with a single-writer connection in the backend and multiple reader connections. Project IDs, repository/checkout relationships, non-secret configuration, and command records survive restart. Each consequential command requiring provenance/reconciliation has a durable request identity, requester/automation source, scope, target, time, and initial state **before dispatch**. A write failure rejects dispatch; acknowledgements/outcomes are stored separately. Test restart, concurrent requests, and storage failures.
- [ ] **AC05: Reconciliation and data authority.** Restart/restore reconciles unfinished `dispatched` commands against engine-host / GitHub without blind resend. External runs are assigned a project only if their relationship is verified; unattributed runs do not receive project-scoped actions. Deleted caches can be rebuilt without deleting registry/history/engine/forge state. Stale data displays its source and observation time; unavailable, absent, malformed, and incomplete/truncated are distinguished. Test ambiguous acknowledgements, external contradictions, pagination, and unavailable authorities.
- [ ] **AC06: Safe removal, backup, and migration snapshots.** Registration removal is rejected while runs are active; once permitted, it leaves a tombstone and command attribution, without deleting repositories/checkouts/worktrees/evidence. Command metadata/evidence links are retained without automatic pruning, especially unresolved commands. Consistent backup via SQLite VACUUM INTO includes schema/version compatibility; restore requires confirmation, checkout/identity revalidation, and reconciliation. An automatic pre-migration snapshot is created before schema upgrades; migration failure preserves data and holds dispatch.

### Intake, execution, and delivery

- [ ] **AC07: Structured intake.** The operator can read, review, publish/update specs and tickets and assess/change readiness through structured actions, without a chatbot or shell. Previews display the target repository, changes, admission/hold/exclusion reasons, and label effects. Publication/readiness each require their own permission; parent specs and wayfinders remain planning-only, not executable work.
- [ ] **AC08: Admission and exact-target enforcement.** Before side effects, direct/scheduled/continuation/spec-dispatch paths verify the target repository/issue/PR, executable contract, canonical labels, prerequisites, active claim, and current state. `wontfix` excludes; `needs-info`, `ready-for-human`, `needs-triage`, unlabeled/unknown-only, and unresolved/unverifiable dependencies hold. Legacy `factory:*` does not grant authority. Subtickets dependent on other tickets have their local integration status (`integrated_to_branch`) validated. The issue actually executed must be identical to the admitted target; races or unavailable state reject/hold.
- [ ] **AC09: Spec coordination via targeted primitives.** Factory coordinates admitted child selection/claims, explicit target binding, and serialized integration; Animus executes targeted work through individual execution primitives (`animus-implement` with a frozen contract per subticket), not an unbound general loop picker. Membership/dependencies/contract snapshots and ownership remain reconcilable after drift/restart. Competing coordinators do not work on/integrate the same child without authorization. Completion status alone is not authored-green evidence.
- [ ] **AC10: Isolated work and one final PR.** Subtickets run in isolated checkouts/worktrees/branches whose repository, expected starting SHA, and exclusive writer are proven before the first node and throughout execution. Contract-compliant results are integrated serially into the local integration branch (`integrated_to_branch`), unblocking dependencies for subsequent subtickets without prematurely closing GitHub issues. Conflict/drift/restart holds integration without losing attribution. Exactly one final PR is created for the spec and no PRs per subticket; a standalone ticket produces one PR.
- [ ] **AC11: Final-candidate evidence and landing.** Subtickets run checks proportionate to their contracts, without requiring a black-box app check on each isolated branch. The final integrated spec candidate on the integration branch, and the final standalone-ticket candidate, receive applicable independent black-box checks and review. The final PR may be created before those checks finish, but readiness/merge remains held. Evidence binds the trusted spec, PR, head, relevant base/merge tree, runtime/setup, and trusted producer; material changes invalidate evidence. A landing guard prevents merge when the candidate differs from the verified tree.
- [ ] **AC12: Tiered action matrix and freshness.** Backend and host revalidate the action, project, resource, gate, expected state/candidate, and authorization at execution time. Read-only/telemetry uses a short TTL (30-60 seconds). Reversible controls (pause/brake) require 1-click confirmation. Consequential actions (Launch, Cancel, Approve Gate, Prepare Promotion PR, Merge/Deploy) require a confirmation modal displaying the target branch, candidate SHA, and issue numbers, plus a **live freshness check ≤10 seconds**. On drift (changed SHA/prerequisites), the action is rejected (fail closed). Auto-merge and auto-deploy remain independent policies.
- [ ] **AC13: Honest command outcomes.** The operator can distinguish rejected, accepted/acknowledged, running/waiting, succeeded, failed, partial, and unknown, with provenance. Duplicate requests are recognized to the extent the seam supports, without promising exactly-once. A timeout after PR creation displays unknown/partial, subsequently reconciled; it does not automatically create a duplicate. A prerequisite freshness failure rejects effects with a specific reason.
- [ ] **AC14: Scoped controls and schedules.** Schedule pause, project/global launch brake, per-run cancellation, process termination, and native authored gate/resume are not treated as equivalent. A global brake prevents launches across the installation without removing project brakes; releasing the global brake does not release project brakes. Brake/pause does not claim active runs have stopped or candidates are frozen. Direct/scheduled paths enforce the applicable verified brake; an unknown required brake holds launch. Per-run control is available only after proving scope, authorization, native response, and effects/cleanup; unsupported is not a successful no-op.
- [ ] **AC15: Approval, promotion, and deployment.** Approval names a specific gate/project/target/candidate and is verified against current engine/forge state, not a historical waiting state. Promotion displays source/target/candidate and prerequisites, and reports PR creation and brake/freeze as separate effects. PR created does not mean approved, merged, frozen, or deployed. Merge and deployment each require their own evidence/permission; release-complete applies only when all policy-required stages are verified. Test overlap, stale candidates, no changes, and PR-created/brake-failed without automatic rollback/retry.
- [ ] **AC16: End-to-end safe evidence/reports.** Host → backend → `@animus/client` → web serves only verified, allowlisted metadata/artifacts, including Markdown reports with the correct transport/content type. Failed/missing/stale verification does not produce fabricated PASS/approved/report-available states. API unavailability is not mapped to not-found. Synthetic secret/holdout-like payloads do not pass through responses, reports, errors, logs, or live/replay.

### Operator UI and transport

- [ ] **AC17: Scoped frontend and navigator.** The frontend is cleanly migrated to React/TypeScript on the agreed Vite toolchain, TanStack Router/Query/Form, and Zod; all operator operations go through `@animus/client` and operator schemas. Routes/query keys carry project/resource identity. A bounded/searchable sidebar shows one row per spec (with verified integrated progress, e.g. `2/10`) and standalone issue, without a nested ticket submenu; planning records are marked. Spec details include a child/dependency DAG visualization and branch integration status.
- [ ] **AC18: Live observation and recovery.** A project/lap-scoped WebSocket connection manager uses a bounded buffer, reconnect, deduplication, and gap signaling; snapshots/query reconciliation establish initial/recovered truth. Lifecycle events are invalidation hints, not a monotonic state log or proof of completeness. Duplicate/out-of-order/late events do not turn completed into running without current authoritative evidence. Reconnect does not blindly retry consequential commands.
- [ ] **AC19: shadcn UI primitives & x.ai visual tokens.** The design adopts visual tokens from the brief/x.ai (dark high-contrast `#0A0A0A`, container `#1A1A1A`, border `#1F2228`, high-contrast text, orange accent `#FF6308`, and GeistMono/Sans fonts), but all interactive components use **pure shadcn/ui primitives** (Base UI, Dialog, Forms, Tabs, Buttons, Badges, Table) without fake terminal windows or fake marketing chrome. Long logs are virtualized; states (loading, empty, error, stale, disconnected) are honest, without demo data. Keyboard accessible, with visible focus, and passes WCAG AA contrast testing.

### Architecture, installation, harness, and distribution

- [ ] **AC20: Executable boundaries.** The web/backend/engine-host/contracts/client workspaces are retained with small, explicit, feature-based public interfaces. Feature callers do not import another feature's internals or another owner's storage. Browser/client does not import app/server/host privileges; contracts do not depend on app internals. Operator/host schema entrypoints are separate, types derive from runtime schemas, and there is no root export-all. Deliberate forbidden imports fail the architecture check; allowed feature calls continue to pass.
- [ ] **AC21: One installation, two private processes.** Launcher/configuration/start/stop/recovery operate backend and engine-host as one application, with static web/API on one localhost origin by default. Engine-host is accessed only by the backend through a validated private interface, not a browser endpoint or arbitrary engine/shell dispatch. Partial startup/shutdown failures are reported per process. Application shutdown is not equated with cancellation of all detached native work.
- [ ] **AC22: Private access and protected credentials.** Localhost loopback bind by default (`127.0.0.1`). The local session secret file has `0600` permissions. Private/Tailscale access is disabled by default; if enabled (`FACTORY_REMOTE_ACCESS=true`), it requires a static operator authentication token/passphrase, private IP binding, and strict CSRF protection. Forge credentials (GitHub Token / API keys) are stored in a server-side protected environment / OS credential manager, never in console SQLite, the browser bundle/localStorage, or public API telemetry.
- [ ] **AC23: Ordinary offline verification.** Bun tests cover backend/persistence/contracts/host integration with in-memory SQLite and synthetic forge/engine transports. Vitest/React Testing Library tests frontend/component state; Playwright tests critical single-origin operator journeys with a mock backend. Ordinary suites do not use live external networks or credentials; loopback fixtures are allowed for transport/process tests. Passing mocks are not independent runtime evidence.
- [ ] **AC24: Fail-closed CI.** GitHub Actions uses a qualified locked Bun toolchain and frozen dependency installation. Sequential gates: static lint/format/architecture; typecheck/unit/contract/offline integration verification; frontend build and backend/host packaging. Required browser verification from AC23 is explicitly wired into the pipeline. Deliberate failure at each gate stops the candidate from advancing; candidate artifacts are not published until all required gates pass.
- [ ] **AC25: Unified release and recovery.** The release bundle has immutable SemVer + Git SHA, matching web/backend/engine-host versions, a frontend served by the Bun backend launcher, and recorded and checked engine pin/schema compatibility. Installation/updates reside in a self-contained application directory separate from managed project state. Before schema upgrades, create a consistent SQLite snapshot (`console.db.pre-vX.X.X.bak`); failure preserves data and keeps dispatch closed. Rollback restores the previous binary release and the pre-migration database snapshot with explicit operator confirmation. Target matrix: macOS (darwin-arm64, darwin-x64) and Linux (linux-x64, linux-arm64).
- [ ] **AC26: Aligned cutover and evidence.** All callers of changed features, contract/client, scripts/configuration, and active guidance use the correct TypeScript patterns/commands; still-active legacy Python instructions are reconciled. Evidence artifacts record the source spec/AC, scenario/command, result PASS/FAIL/BLOCKED/NOT RUN, relevant candidate/head/base, and artifact location. Rerun affected checks after candidate/base changes.

## Boundary

### Included

All AC01–AC26 outcomes: project registration/isolation; structured intake and commands; console persistence/recovery (SQLite WAL); Factory spec coordination via targeted primitives (`animus-implement`); evidence/final delivery gates; React operator frontend with shadcn primitives and x.ai tokens; private installation/access; executable architecture/testing; and application distribution/update/rollback with snapshots.

Corrective admission/evidence work from the research is part of the completion requirements. Per-feature contract migrations include all necessary callers.

### Excluded

- Public multi-tenant SaaS, billing, marketplace plugins, or multi-host worker/fleet orchestration.
- Conversational chatbot, interactive shell, unmanaged AI runner, replacement workflow state machine/scheduler, or private fork of the Animus workflow.
- A local Markdown tracker or operation without GitHub.
- A generic CI/CD platform replacing the forge; new mobile/desktop clients.
- Weakening the evaluator, accessing private holdout, builder self-approval, or the application changing protected governance to pass gates.
- Permanent deletion of console records, repositories, checkouts, worktrees, or evidence as an effect of registration removal.
- Release publication, provisioning, branch-protection changes, launch, merge, promotion, or deployment as an effect of approving the specification document.

## Verification

### Public seams

The primary seam is the operator API through `@animus/client` against the backend, with the same request/response/error schemas used by the web. Test observable results, refusals, scope, provenance, and state transitions, not constructor wiring or folder counts.

Supporting seams:
1. **Private host/native adapter + real processes:** explicit target, pre-node checkout identity/ownership, native acknowledgement/reconciliation, backend/host lifetime, controls, and cleanup. Synthetic native subprocess/forge adapters are used for ordinary tests; actual configured native behavior is a separate qualification.
2. **SQLite persistence:** command-before-dispatch transactions, WAL concurrency, restart/crash ambiguity, corruption/migration/backup/restore. Use in-memory DBs for unit/integration isolation and temporary real files for durability/restart proof.
3. **Single-origin browser:** Playwright for project switching/multiple tabs, forms/confirmation modals, sidebar/spec progress, evidence/reports, connection recovery, and keyboard/focus journeys. A mock backend proves UI behavior, not live native capability.
4. **Architecture/CI/release commands:** negative forbidden-import/type/test controls, gated packaging, clean installation, migration snapshot/rollback.
5. **Independent final-candidate verification:** current trusted producer/review provenance, black-box app evaluation, head/base/tree binding, and enforced landing.
